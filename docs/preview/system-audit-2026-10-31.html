一、P0 严重问题（19 项）

判定标准：会导致金额算错、数据静默丢失、越权读写他人项目，或让审批/审核形同虚设。

A. 金额与口径错（7 项）

P0-1草稿报量直接算进产值和利润

甲方报量新建默认是"草稿"，但月报/成本中心/首页只排除了"作废"，草稿全部计入产值，越录越多、产值越虚高。

证据：api/client-reports/route.ts:241（强制 draft）、monthly/summary:196、lib/data-aggregation.ts:588-595（注释写"仅已审核"、实际只排 voided）、dashboard:220

建议：统一走 isReviewedStatus；或业务确认"草稿要算"后，把注释和标签改对。

P0-2供应商"应付=0"被当成空值，回退成结算全额

最终结算付款比例 0% 时应付本就是 0，但代码 payable_amount || settlement_amount 把 0 当空，月报把整笔结算算成应付，供应商未付和资金缺口虚增，还和成本中心对不上。

证据：monthly/summary:372；对照 data-aggregation:86-90（只对 null 回退）

P0-3未发工资只算当月、且用应发口径，跨月欠薪永远看不到

"未发工资/欠薪风险"只查了报告月当月工资，且用 gross_pay；上月欠的工资不计入，earliestUnpaidMonth < reportMonth 永远不成立，风险灯永远不红。累计应付与未付也对不上。

证据：monthly/summary:203,693,697-702,830,808-817

P0-4"现金净流"把税费、应计费用当成了现金支出

本月实际支付 = 已发工资 + 供应商付款 + 当月综合费用 + 当月材料 + 当月税费。税费和没付现的费用/材料被算成现金流出，部分发放被忽略，班组付款没计入，现金净流与趋势图口径也不一致。

证据：monthly/summary:673-683,1275

P0-5成本中心/资金看板漏计老表 payments 的已付款

供应商结算同时读老表和新表，但"已付"只读新表 supplier_payments，老表的历史付款完全不算 → 已付偏低、未付偏高，与月报给出的付款率不一样。

证据：data-aggregation:730-756 vs monthly/summary:200-201,394-429

P0-6Excel/PDF 导出字段名对不上，导出的金额是 0

summary 返回 totalSettlement/totalPaid/…，导出代码却读 settlementAmount/paidAmount/…；回款滞后同理。导出的"供应商付款明细""回款滞后"大量为 0，与页面不一致。

证据：summary:950-957,1035-1042 vs export-excel:192-201,224-236、export-pdf:428-440

P0-7供应商结算明细里，每张结算单都被填了"全部已付"

同一供应商+项目的所有付款，被重复算到每一张结算单头上；前端求和/导出时已付翻倍、未付失真，风险排序也错。

证据：monthly/summary:848-855,858,1330-1337

B. 数据污染与丢失（6 项）

P0-8供应商结算导入/新增完全无查重

同一个 Excel 导两次，结算金额就双份计入成本。只有"总结算"有拦截，进度结算没有任何保护。

证据：supplier-contracts/settlements/import:171-187、supplier-settlements/route.ts:218-234、建表无业务唯一索引

P0-9甲方回款导入无查重 + 未知状态静默变"已完成"

回款重复导入直接翻倍；Excel 里写"待确认/作废/已取消"等未映射文本，一律 || 'completed' 当作已回款，未收余额可能出现负数。

证据：client-payments/import:200-201,224-229；报量导入反而有查重（client-reports/import:229-243）

P0-10零星材料查重只加载前 1000 行，超过就失效

查重集合一次性 select，没有分页。第 1000 行以后的记录不在集合里，重导后半段全部重复入库（之前的 1191 条冗余就是这么来的）。

证据：miscellaneous-materials/import:301-307（未用 lib/fetch-all-rows.ts）

P0-11供应商结算"录入即已审核"，绕过刚恢复的审批流

新增/导入直接写 reviewed，永远不进"待审核"；而页面已经有提交审核/反审核按钮。审批语义失效，导入还能直接触发合同完结锁定。

证据：supplier-contracts/settlements/route.ts:314、.../import:182、supplier-settlements/route.ts:228

P0-12班组结算审批通过后，生成分账工资失败被吞掉

状态已经置为"已通过"（计入成本），但生成工资抛错只 console.error，工人冲突只 warn。结果：成本算了、工资台账漏人，且没有重试入口。

证据：team-settlements/workflow:185-194,239-263

P0-13删除供应商合同/项目时不清理子表，留下孤儿数据

合同删除时子表失败只 log 后继续删；supplier_settlements/payments/logs 三张表没有任何外键。删项目更简单粗暴：只 delete projects，工人变"无项目"，费用/材料/合同留下悬挂 project_id，成本归零。

证据：supplier-contracts/[id]:258-288、projects/[id]:306-331（已有 related-counts 接口却没人调用）

C. 越权与审批（6 项）

P0-14撤销超管最长 7 天不生效

权限码 60 秒刷新，但 is_super_admin 直接用登录时写进 JWT 的值，从不回写。被降级的人仍能调超管接口。

证据：lib/api-auth.ts:99-111、lib/auth.ts:154、proxy.ts:222

P0-15签证可以"自己提、自己签、自己结"，还能跨项目操作

submit/review/settle 三个接口都只校验 visas:edit，不校验审批人身份，也不校验项目范围。一个预算员账号能走完全流程，A 项目的人能改 B 项目签证。

证据：visas/[id]/submit:12,31-66、review:17,48-97、settle:12,30-52

P0-16多个写接口可以写任意项目的数据

work-items、project-internal-addons、internal-addon-settlements、subitem-monthly-reports 都只校验权限码，不校验 body 里的 project_id/subitem_id 属于自己，可篡改他人项目工程量与报量。

证据：work-items:170-190、project-internal-addons:58-128、subitem-monthly-reports:59-70

P0-17班组结算反审核可能丢掉发放记录和生活费抵扣

只检查了 salary_payments.salary_id 和回单明细，但发放记录的 salary_id 可能为空（按工人+项目+月匹配），生活费抵扣是 SET NULL。检查与删除也不同事务 → 反审核会静默删掉已发流水或断开抵扣链。

证据：team-settlements/workflow:104-122,268-294

P0-18供应商结算"提交审核"对普通财务/预算员必然 403

按钮所有人可见，接口 /api/review 要求 system:manage。只有结算编辑权限的人一点就报无权，结算单永远卡在草稿、不计成本——和之前"草稿不计入"的故障同一类。

证据：supplier-contracts/settlement/page.tsx:588-614、lib/route-permissions.ts:297

P0-19月报切月份不清空旧数据，还能把上月数据存成新月份快照

切月只 setLoading，不清 data、无请求序号；失败时旧数据仍在。此时点"存档"→ 上月数字被归档成新月份，历史月报永久错。

证据：reports/monthly/page.tsx:245-256,594,395-402

四、数据污染风险清单

  1. 导入无查重：供应商结算、甲方回款、历史中标价（旧批量）、工人（无身份证）——重复导入直接翻倍。
  2. 查重集被 1000 行截断：零星材料（已验证发生过 1191 条冗余）。
  3. 状态静默默认：回款未知状态→completed；供应商结算→reviewed。
  4. 金额解析：千分位被截断（"1,234"→1）、NaN→0/null。
  5. 日期解析失败回退今天：材料采购日期错到当月。
  6. 删除不清理子表：合同删了结算还在；项目删了材料/费用/合同还挂着旧 project_id。
  7. 反审核物理删除工资：无审计快照，删了找不回。
  8. 跨表重复录入：同一张发票既录综合费用又录零星材料，成本双扣（需业务确认是否发生过）。
  9. sequence 回卷风险：删掉最大 id 后若 setval(max)，新数据会复用旧 id，孤儿数据"复活"挂到新记录上（需实测）。
