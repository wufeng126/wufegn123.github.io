# P0 功能优化方案（现有构架对照版）

> 基于真实代码核对：`schema.ts`（表结构）、`quantity-reporting/page.tsx`（报量前端 4855 行）、`business-logic.ts`（校验钩子）、`data-aggregation.ts`（成本口径）
> 原则：**复用现有表/API/校验模式，不另起炉灶**；每项标注 现有基础 → 缺口 → 落地方案 → 涉及文件

---

## 核心发现（决定优化形态的三件事）

1. **三层价格已存在但未分离**：`work_item_subitems` 已含 `contract_price`（合同价）/ `limit_price`（限价）/ `unit_price`（单价），但前端大量 `limit_price || contract_price` 兜底 → **限价形同虚设，实际成本（对下结算价）没有独立字段记录在分项上**
2. **月度报量/结算已分表**：`subitem_monthly_reports`（对上报量）+ `subitem_monthly_progress`（对下结算）→ 勾稽数据源齐，缺"回款维度 + 结转视图 + 差异提示"
3. **超限校验完全没有**：结算校验只有"付款不超应付"，无"单价 vs 限价"拦截

## P0-1 报量-结算-回款月度勾稽

**现有基础（全部已有）**
- `work_item_subitems`（预算量/完成量/合同价/限价）+ `subitem_monthly_reports`（月度对上报量）+ `subitem_monthly_progress`（月度对下结算）
- `client_reports`（甲方报量，已审核）+ `client_payments`（甲方回款）
- `quantity-reporting` 页已有"月度报量/月度结算"录入入口（`monthlyReportDialog`、`settlementDialog`）

**缺口**
- 没有一张表/视图把"报量 vs 结算 vs 回款"按分项-月放一起做结转；差异靠人肉核对
- 报量录入无"累计 > 预算量"强制确认（有预警但可绕过）

**落地方案（纯聚合 + 校验钩子，不新增表）**
1. 新增 `getSubitemMonthlyReconciliation(client, { projectId?, yearMonth? })` API：
   - 按月/分项聚合：期初结余（上月累计报量−累计结算）＋ 本月报量 − 本月结算 − 本月回款（回款按 `client_payments` 项目级，无法到分项 → **回款只做项目级汇总列**，分项级做"报量 vs 结算"两栏，回款放在项目汇总行）
   - 口径说明：`subitem_monthly_reports` 为对上报量、`subitem_monthly_progress` 为对下结算——**两者本来就在不同表**，差异 = 报量 − 结算，天然是"对上 vs 对下"差额
2. 报量/结算录入处加前置校验（复用 `quantity-reporting` 现有 `handleSave` 逻辑）：
   - 累计报量 > 预算量 → 强制 `confirm`（用现有 `useConfirm`）
   - 月度报量 − 月度结算 差异 > 30% → 提示"可能少结/多报"（非阻塞 toast）
3. 前端在 `quantity-reporting` 新增"**勾稽台账**"Tab（新视图组件，从 4855 行上帝组件中独立出来——顺带缓解组件过大）

**涉及文件**
- 新增：`src/lib/subitem-reconciliation.ts`（聚合）+ `src/app/api/subitem-reconciliation/route.ts`
- 修改：`quantity-reporting/page.tsx`（新增 Tab + 前置校验）、`route-permissions.ts`（注册新 API）

**工作量**：中。数据源 100% 现成，纯聚合。

## P0-2 限价过程控制（超限拦截 + 三层价格落地）

**现有基础**
- `work_item_subitems.limit_price`（限价字段已有）
- `business-logic.validateSupplierSettlementPayment`（结算单校验模式可复用）
- `review` 统一审核流（超限审批可选复用）

**缺口**
- 前端 `quantity-reporting` 的"结算价"列显示 `limit_price || contract_price`（:3223）→ **限价没填时分项退回合同价当结算价，语义错误**
- 结算单保存（`api/supplier-contracts/settlements` 或 `team_settlements` 写入）**无单价 vs 限价校验**
- 超限无留痕字段（`supplier_settlements` 无 `over_limit`/`over_limit_reason`）

**落地方案**
1. **语义修正**：前端结算价列改为显示实际结算单价（来自月度结算记录的数量/金额），不再 `limit_price || contract_price` 兜底；`contract_price` 只用于"合同收入"、`limit_price` 只用于"成本线"
2. **超限校验钩子**：新增 `validateSettlementLimitPrice(client, { subitem_id, unit_price, limit_price })`（仿 `validateSupplierSettlementPayment` 模式），在结算保存链路调用；超限 → 返回 `{ overLimit, overRatio }`，前端弹确认框（填原因，`useConfirm` 扩展支持原因输入）→ 提交时把 `over_limit=true, over_limit_reason` 存入结算记录
3. **留痕字段**：`supplier_settlements` / `team_settlements` 加 `over_limit BOOLEAN DEFAULT false`、`over_limit_reason TEXT`（小迁移，`migrations/` 加一个 SQL）
4. 超限数据进风险预警（复用 `notifications` 类型 `cost_warning` 或新增 `over_limit`）

**涉及文件**
- `business-logic.ts`（新校验函数）、结算 route（supplier-contracts/settlements、team-settlements）、`quantity-reporting` 前端（结算录入弹超限确认）
- `migrations/`（2 个字段）、`schema.ts`（同步定义）

**工作量**：中。校验模式现成，主要新增字段 + 前端弹窗。

## P0-4 进度计划三态闭环

**现有基础**
- `project_progress_tasks`（计划任务/里程碑）+ `project_progress_task_quantities`（任务工程量）
- `construction_log_progress_entries`（**施工日志关联进度任务已存在**：log_id + progress_task_id + actual_progress）— 数据链路已经通了！
- `progress-management` 页面 + `api/progress-management`
- `construction-log-risk`（风险规则引擎）

**缺口**
- `construction_log_progress_entries` 是"日志→进度"的落点，但**前端日志提交表单没有引导选择进度任务**（字段存在、UI 未接）
- 进度滞后无"计划 vs 实际"自动对比与风险触发（风险引擎基于日志内容/评论，非进度对比）

**落地方案**
1. **日志提交引导关联**：`construction-logs/new` 表单加"关联进度任务"选择器（该项目 `progress_tasks` 下拉）→ 提交后写 `construction_log_progress_entries.actual_progress`（数据链路现成，只接 UI）
2. **三态看板**：新增 `getProgressComparison(client, { projectId })` API → 计划（tasks 汇总）vs 实际（entries 汇总）vs 完成量（task_quantities），滞后 >10% 标红；`progress-management` 页加三态视图（或独立 Tab）
3. **滞后自动进风险**：在 `notifications/check` 的检测任务中加"进度滞后扫描"（仿现有 `checkCostWarnings` 模式），滞后任务生成 `construction_log_alert` 类通知

**涉及文件**
- `construction-logs/new`（加选择器）、`api/construction-logs`（写 entries 时支持 task 关联——已有字段）
- 新增 `lib/progress-comparison.ts` + `api/progress-management/comparison`（或并入现有）
- `notifications/check`（加进度滞后检测）

**工作量**：中。数据链路已通（`construction_log_progress_entries` 表就是为此设计的），主要是 UI 接入 + 聚合视图。

## P0-6 成本三层对比

**现有基础**
- `work_item_subitems`：`budget_quantity`（预算量）+ `contract_price`（合同价）+ `limit_price`（限价）+ `completed_quantity`（完成量）
- `cost-center`（11 项口径，`data-aggregation.calculateProjectCost`）+ 三看板
- `subitem_monthly_progress`（对下结算量，即实际成本量）

**缺口**
- 成本中心是**项目级**汇总，没有**分项级**"合同收入 vs 限价成本 vs 实际成本"三层对比
- 三层价格字段存在但未形成"价差 = 毛利"的展示（前端 `limit_price || contract_price` 混用）

**落地方案**
1. 新增 `getSubitemCostComparison(client, { projectId? })` API：
   - 每分项：合同收入 = `budget_quantity × contract_price`；限价成本 = `budget_quantity × limit_price`（或完成量口径）；实际成本 = 对下结算（`subitem_monthly_progress` 汇总 × 结算单价，或从 `supplier_settlements`/`team_settlements` 按分项关联）
   - 价差 = 合同收入 − 实际成本（毛利）；实际成本 > 限价成本 → 标"超限价"
2. `cost-center` 页新增"**分项三层对比**"Tab（复用现有 `ChartCard`/表格组件），或独立子页
3. 超限/负毛利分项自动进风险预警（与 P0-2 共用超限标记）

**涉及文件**
- 新增 `lib/subitem-cost-comparison.ts` + `api/cost-center/subitem-comparison`
- `cost-center/page.tsx`（加 Tab）、`route-permissions.ts`

**工作量**：中。字段全现成，难点是"实际成本到分项"的关联——`subitem_monthly_progress` 按 subitem_id 关联，链路清晰。

## 修正说明（与之前预览的差异）

- 之前预览把"回款"放到分项级勾稽——实际 `client_payments` 只有项目级，**分项级只能做"报量 vs 结算"，回款放项目汇总**
- 之前预览的限价拦截是独立弹窗——实际复用现有 `useConfirm`（扩展支持原因输入），校验钩子仿现有 `validateSupplierSettlementPayment`
- 三层价格的"实际成本"来源明确为 `subitem_monthly_progress`（对下结算），不是新概念
